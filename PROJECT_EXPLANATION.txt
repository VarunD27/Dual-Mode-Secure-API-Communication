1. PROJECT OVERVIEW & PROBLEM STATEMENT
================================================================================

PROBLEM:
  Modern API communication systems use FIXED protocols (like TLS 1.3) that
  do NOT adapt to changing network conditions. This means:
  - When the network is fast and stable: TLS adds unnecessary overhead
  - When security is critical: a lightweight protocol may be unsafe
  - There is NO system that dynamically BALANCES security vs performance

SOLUTION:
  We built an Adaptive Session-Based Protocol Selection System with:
  - TWO communication modes running simultaneously:
      (a) Secure Mode: Flask HTTPS with TLS 1.3  (Port 5000)
      (b) Fast Mode:   Custom TCP with AES-GCM   (Port 6000)
  - A 5-Factor Decision Engine that SCORES both protocols
    (latency, handshake, payload, security, reliability)
  - A Hysteresis Controller that prevents rapid switching
  - Network Simulation via dashboard (delay + error rate injection)
  - A Real-Time Dashboard with 5 charts for visualization
  - Session-wise handshake optimization
  - Emergency protocol switch on persistent failures

2.3  server/tls_server.py  (TLS/HTTPS Server)
--------------------------------------------------------------------------------

PURPOSE: A Flask web server running over HTTPS with TLS 1.3 on port 5000.

HOW IT WORKS:
  1. Flask is a Python web framework that handles HTTP routing
  2. We wrap it with SSL/TLS using Python's ssl module
  3. The server loads the certificate (server.crt) and key (server.key)
  4. All communication is encrypted via TLS 1.3

KEY FUNCTIONS:

  main()
    - Parses command-line arguments (--port, --delay, --packet-loss)
    - Loads TLS certificates from certs/ directory
    - Creates ssl.SSLContext with PROTOCOL_TLS_SERVER
    - Sets minimum_version to TLSv1_3 (enforces TLS 1.3 only)
    - Starts Flask with ssl_context parameter

  @app.before_request -> apply_network_conditions()
    - Flask decorator that runs BEFORE every request
    - Simulates packet loss if PACKET_LOSS_RATE > 0
    - Calls inject_delay(ARTIFICIAL_DELAY_MS) to simulate latency

  ROUTE HANDLERS:
    @app.route("/api/health")   -> Calls handle_request("health")
    @app.route("/api/data")     -> Calls handle_request("data")
    @app.route("/api/echo")     -> Calls handle_request("echo", payload)
    @app.route("/api/compute")  -> Calls handle_request("compute")
    @app.route("/api/set_delay")-> Dynamically changes the delay value
    @app.route("/api/set_packet_loss") -> Dynamically changes packet loss rate

IMPORTANT CLASSES USED:
  - ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
      Creates a TLS context for the server side
  - context.minimum_version = ssl.TLSVersion.TLSv1_3
      Forces TLS 1.3 (the latest and most secure version)
  - context.load_cert_chain(certfile, keyfile)
      Loads our self-signed certificate and private key

TLS 1.3 HANDSHAKE (what happens under the hood):
  1. Client sends ClientHello (supported ciphers, TLS version)
  2. Server responds with ServerHello + certificate + key share
  3. Client verifies certificate, sends key share
  4. Both sides derive session keys
  5. Encrypted communication begins
  NOTE: TLS 1.3 uses a 1-RTT handshake (older versions used 2-RTT)

2.4  server/tcp_server.py  (Custom TCP Server)  [DETAILED]
--------------------------------------------------------------------------------

PURPOSE: A raw socket server with a CUSTOM handshake protocol and
         AES-256-GCM encryption. This is the "lightweight" alternative
         to TLS that reduces protocol overhead.

HOW THE CUSTOM TCP SERVER WORKS (STEP BY STEP):

  STEP 1: Server Startup
    - Creates a TCP socket using socket.socket(AF_INET, SOCK_STREAM)
    - AF_INET = IPv4 addressing
    - SOCK_STREAM = TCP (reliable, ordered byte stream)
    - Binds to 0.0.0.0:6000 (listens on all network interfaces)
    - Calls socket.listen(5) to accept up to 5 queued connections

  STEP 2: Accept Connections
    - server_sock.accept() blocks until a client connects
    - When a client connects, spawns a new THREAD to handle it
    - This allows multiple clients simultaneously

  STEP 3: Secure ECDH-based Handshake (Authentication + Key Exchange)
    
    Phase A: Client Authentication
      - Client sends HELLO JSON with timestamp and HMAC signature
      - Signature = HMAC-SHA256(client_secret, timestamp)
      - Server validates timestamp (must be within 30 seconds)
      - Server validates signature against pre-shared client_secret
      - If validation fails, connection is closed
    
    Phase B: ECDH Key Exchange
      - Server generates ECDH key pair (SECP256R1 elliptic curve):
          server_private_key = ec.generate_private_key(ec.SECP256R1())
      - Server serializes public key as PEM and sends to client
      - Client sends back its ECDH public key (PEM format)
      - Both perform ECDH key exchange:
          shared_secret = server_private_key.exchange(ec.ECDH(), client_public_key)
      - AES-256 key derived using HKDF-SHA256:
          aes_key = HKDF(shared_secret, algorithm=SHA256, 
                        length=32, salt=None, info=b'handshake data')
      - Now BOTH sides have the same AES-256 key without ever transmitting it

    WHY THIS IS BETTER THAN SIMPLE KEY EXCHANGE:
      - ECDH provides perfect forward secrecy (unique key per session)
      - HMAC authentication prevents unauthorized/spoofed clients
      - HKDF key derivation follows NIST cryptographic standards
      - Timestamp validation prevents old handshake messages from being replayed
      - Still MUCH faster than TLS 1.3 handshake (no cert exchange, no signatures)

    TRADE-OFF WITH TLS 1.3:
      - TLS verifies server identity via X.509 certificate chain
      - TLS has server authentication; our custom protocol does not
      - However, this is acceptable for local networks where clients trust servers
      - ECDH + HKDF provides stronger security than simple random key approach

  STEP 4: Encrypted Communication with Integrity Checking
    
    Message Format:
      [4-byte length header][12-byte nonce][encrypted payload with tag]
    
    Payload Structure:
      {
        "action": "health|data|echo|compute",
        "payload": {...},
        "timestamp": <epoch_seconds>,
        "nonce": "<uuid>",
        "hash": "<sha256_hex>"  <- SHA256 of all fields except hash
      }

    Encryption/Decryption:
      - Each message encrypted with AES-256-GCM
      - Nonce (12 bytes): random for each message
      - AAD (Additional Authenticated Data): "session-bound-data"
      - GCM produces ciphertext + 16-byte authentication tag
      - Tag is verified during decryption (tamper detection)

    Message Processing:
      1. Client creates JSON request with all required fields
      2. Client computes SHA256 hash of request data (excluding hash field)
      3. Client encrypts entire JSON with AES-GCM
      4. Client sends: [4-byte length][nonce+encrypted_data]
      5. Server reads length header, then reads exact number of bytes
      6. Server decrypts and checks authentication tag
      7. Server recomputes SHA256 hash and compares with received hash
      8. Server validates timestamp and nonce (replay protection)
      9. If all checks pass, process request and send encrypted response

    Tamper Detection:
      - GCM authentication tag validates message authenticity
      - SHA256 hash detects any request field modifications
      - Any tampering causes immediate rejection with error response

  STEP 5: Multi-Layer Replay Attack Protection
    
    ReplayProtection Class:
      - Maintains nonce cache (LRU, size: 1000 entries)
      - Timestamp tolerance window: 300 seconds (5 minutes)
    
    Three-Layer Validation Per Request:
      1. Nonce Uniqueness Check:
         - Nonce must not exist in cache (prevents nonce reuse)
         - If unique, add to cache
         - If duplicate, reject with "Request rejected (potential replay attack)"
      
      2. Timestamp Freshness Check:
         - Current_time - request_timestamp must be < 300 seconds
         - Rejects old messages outside tolerance window
         - Prevents replay of very old messages even if nonce is lost
      
      3. Hash Integrity Check:
         - Server recomputes SHA256(request_data)
         - Compares with received hash field
         - Rejects if hashes don't match (data was tampered)
    
    Protection Against Common Attacks:
      - Simple Replay: Prevented by nonce cache + timestamp window
      - Delayed Replay: Prevented by timestamp tolerance
      - Tampering: Prevented by hash + GCM tag
      - Nonce Reuse: Prevented by LRU cache
    
    Error Responses:
      All validation failures send encrypted error response:
        {"status": "error", "message": "<specific_reason>"}

KEY FUNCTIONS:

  generate_aes_key() -> bytes
    - Calls AESGCM.generate_key(bit_length=256)
    - Returns 32 random bytes (256 bits)

  encrypt_message(key, plaintext) -> bytes
    - Creates AESGCM instance with the shared key
    - Generates 12-byte random nonce using os.urandom(12)
    - Encrypts: ciphertext = aesgcm.encrypt(nonce, plaintext, None)
    - AES-GCM automatically appends a 16-byte authentication tag
    - Returns: nonce + ciphertext (concatenated)

  decrypt_message(key, data) -> bytes
    - Splits data: first 12 bytes = nonce, rest = ciphertext
    - Decrypts: aesgcm.decrypt(nonce, ciphertext, None)
    - If the auth tag doesn't match, raises an exception (tamper detected)

  send_framed(sock, data)
    - Packs the length as 4 bytes: struct.pack("!I", len(data))
    - "!I" means network byte order (big-endian), unsigned 4-byte integer
    - Sends length + data in one call: sock.sendall(length + data)

  recv_framed(sock) -> bytes
    - Reads exactly 4 bytes using recv_exact()
    - Unpacks to get the message length
    - Reads exactly that many bytes

  recv_exact(sock, n) -> bytes
    - TCP doesn't guarantee you get all bytes in one recv() call
    - This function loops until exactly n bytes are received
    - Essential for reliable binary protocol communication

  handle_client(client_sock, addr)
    - Handles the entire lifecycle of one client connection
    - Phase 1: Perform HELLO->ACK handshake
    - Phase 2: Loop receiving encrypted requests, processing them,
      and sending encrypted responses
    - Validates nonce/timestamp for replay protection
    - Uses inject_delay() for artificial latency
    - Simulates packet loss if PACKET_LOSS_RATE > 0

2.5  client/network_prober.py
--------------------------------------------------------------------------------

PURPOSE: Probes BOTH servers to measure their real-time performance metrics
         before and during the session. Reads simulation configuration
         from logs/simulation_config.json to include injected delays
         and error rates in probe measurements.

KEY FUNCTIONS:

  _load_simulation_config()
    - Reads logs/simulation_config.json
    - Returns dict with tls_delay_ms, tcp_delay_ms, error_rate
    - If file missing, returns zeros

  probe_tls() -> dict
    - Creates a NEW requests.Session (fresh TCP + TLS connection)
    - FIRST request: measures HANDSHAKE TIME
      (includes TCP connect + TLS handshake + first HTTP request)
      The configured tls_delay_ms is ADDED to the measured time
    - SECOND request: measures RTT (Round-Trip Time)
      (connection already established, measures pure request latency)
      The configured tls_delay_ms is ADDED to the measured time
    - Simulates errors based on configured error_rate
    - Returns: {handshake_time, rtt, payload_size, success, error_rate}

  probe_tcp() -> dict
    - Creates a NEW TCP socket connection
    - Performs HELLO->ACK handshake (measures handshake time)
      The configured tcp_delay_ms is ADDED to the measured time
    - Sends one encrypted health request (measures RTT)
      The configured tcp_delay_ms is ADDED to the measured time
    - Simulates errors based on configured error_rate
    - Returns: {handshake_time, rtt, payload_size, success, error_rate}

  probe_both() -> dict
    - Calls probe_tls() and probe_tcp() sequentially
    - Returns combined results with timestamp

WHY TWO SEPARATE MEASUREMENTS (handshake vs RTT):
  - Handshake Time: The one-time cost of establishing the connection.
    For TLS, this includes the TLS 1.3 handshake (certificate exchange,
    key derivation). For TCP, this is our simple HELLO->ACK exchange.
  - RTT: The ongoing per-request cost after connection is established.
    Shows the raw latency of sending data back and forth.

IMPORTANT: time.perf_counter() is used for timing because it provides
  the highest resolution timer available on the system (nanosecond precision
  on most platforms), much better than time.time().

2.6  client/decision_engine.py
--------------------------------------------------------------------------------

PURPOSE: The BRAIN of the system. Computes a cost score for each protocol
         using a 5-factor weighted multi-metric formula.

THE SCORING FORMULA (ALL VALUES NORMALIZED TO 0-1 RANGE):
  Score = 0.30 * norm_latency + 0.20 * norm_handshake + 0.10 * norm_payload
          + 0.25 * security_cost + 0.15 * reliability_cost

  Where:
    norm_latency = RTT / MAX_RTT (MAX_RTT = 3000ms)
    norm_handshake = handshake_time / MAX_HANDSHAKE (MAX_HANDSHAKE = 3000ms)
    norm_payload = payload_size / MAX_PAYLOAD (MAX_PAYLOAD = 2000 bytes)
    security_cost = 0.2 for TLS, 0.6 for TCP (lower = more secure)
    reliability_cost = error_rate (0.0-1.0)

  LOWER SCORE = BETTER PROTOCOL
  All factors normalized to 0-1 range for fair weighted comparison

KEY FUNCTIONS:

  compute_score(metrics, protocol) -> float
    - Normalizes all metrics to 0-1 range
    - Applies the weighted 5-factor formula
    - Returns normalized cost score

  evaluate(tls_metrics, tcp_metrics) -> dict
    - Computes scores for BOTH protocols using normalized metrics
    - Determines which is recommended (lower score wins)
    - Calculates score_advantage as a percentage
    - Returns: {recommended, score_advantage, tls_score, tcp_score}

  _normalize(value, max_value) -> float
    - Returns min(value / max_value, 1.0)
    - Ensures all normalized values stay in 0-1 range

  compute_security_cost(protocol) -> float
    - Returns 0.2 for TLS (very secure)
    - Returns 0.6 for TCP (less secure but acceptable)

  compute_reliability_cost(protocol, error_rate) -> float
    - Returns error_rate directly (already 0-1)
    - Higher error rates increase cost and disfavor protocol

EXAMPLE (WITH NORMALIZED METRICS):
  Assuming: MAX_RTT=3000ms, MAX_HANDSHAKE=3000ms, MAX_PAYLOAD=2000B
  
  TLS metrics: RTT=85ms, handshake=120ms, payload=512B, error_rate=0.0
  Normalized TLS: 0.028, 0.040, 0.256, security=0.2, reliability=0.0
  TLS score = 0.30*0.028 + 0.20*0.040 + 0.10*0.256 + 0.25*0.2 + 0.15*0.0
            = 0.0084 + 0.0080 + 0.0256 + 0.0500 + 0.0 = 0.0920
  
  TCP metrics: RTT=30ms, handshake=15ms, payload=480B, error_rate=0.0
  Normalized TCP: 0.010, 0.005, 0.240, security=0.6, reliability=0.0
  TCP score = 0.30*0.010 + 0.20*0.005 + 0.10*0.240 + 0.25*0.6 + 0.15*0.0
            = 0.0030 + 0.0010 + 0.0240 + 0.1500 + 0.0 = 0.1780

  Recommended: TLS (score 0.092 < 0.178)
  Advantage: (0.178 - 0.092) / 0.178 * 100 = 48.3%
  
  NOTE: Security weight (0.25) heavily favors TLS. Weights can be tuned
        for different scenarios (latency-sensitive, security-critical, etc.)

2.7  client/hysteresis_controller.py
--------------------------------------------------------------------------------

PURPOSE: Prevents OSCILLATION (rapid back-and-forth switching) between
         protocols. Adds STABILITY to the protocol selection.

WHAT IS HYSTERESIS?
  In engineering, hysteresis means a system resists changing state until
  the input exceeds a significant threshold, and maintains that state
  even if the input drops slightly below the threshold.

  Real-world analogy: A thermostat doesn't turn on/off at exactly 72F.
  It turns on at 70F and off at 74F. This prevents constant on/off cycling.

RULES FOR SWITCHING:
  1. Candidate protocol must show >15% score advantage
  2. Must HOLD that advantage for 3 CONSECUTIVE checks
  3. Switching only happens at safe points (after request completion)

KEY FUNCTIONS:

  should_switch(evaluation) -> dict
    - Takes the decision engine's evaluation result
    - CASE 1: If recommended == current protocol -> reset counter, no switch
    - CASE 2: If advantage < 15% -> too small to bother, reset counter
    - CASE 3: If advantage >= 15% AND same candidate:
        * Increment consecutive_count
        * If count reaches 3 -> TRIGGER SWITCH
        * If count < 3 -> still accumulating, no switch yet
    - CASE 4: If a NEW candidate appears -> reset counter to 1

  get_current_protocol() -> str
    - Returns "TLS" or "TCP"

  force_protocol(protocol)
    - Manually override (for testing or emergency switch)

INTERNAL STATE:
  - current_protocol: The protocol currently in use
  - candidate_protocol: The challenger protocol
  - consecutive_count: How many times in a row the candidate has won

2.8  client/session_manager.py
--------------------------------------------------------------------------------

PURPOSE: Manages the ACTIVE CONNECTION to whichever server is currently
         selected. Handles connecting, disconnecting, switching, and
         sending requests. Includes session-wise handshake optimization
         and simulation config reloading.

KEY FUNCTIONS:

  connect_tls()
    - Creates a requests.Session (HTTP session with keep-alive)
    - Measures and stores handshake time in _last_handshake_time['TLS']
    - Makes a test request to verify the connection works
    - Sets active_protocol = "TLS"

  connect_tcp()
    - Creates a raw TCP socket
    - Performs HELLO->ACK handshake
    - Measures and stores handshake time in _last_handshake_time['TCP']
    - Extracts and stores the AES key
    - Sets active_protocol = "TCP"

  switch_to(new_protocol)
    - If different from current: closes old connection, opens new one
    - Calls connect(new_protocol) internally

  send_request(action, payload) -> dict
    - Dispatches to _send_tls_request() or _send_tcp_request()
      based on active_protocol
    - Reloads simulation_config.json every 2 seconds
    - Both measure RTT using time.perf_counter()
    - Both add _rtt_ms and _payload_size to the response
    - Both inject configured artificial delay into RTT
    - Both simulate errors based on configured error_rate
    - Both retry up to 3 times on failure

  _send_tls_request(action, payload)
    - Uses self._http_session.get() or .post() with verify=False
    - verify=False because we're using self-signed certificates
    - Applies tls_delay_ms from simulation config
    - Simulates error if random() < error_rate
    - Retries up to 3 times with exponential backoff
    - Returns JSON response

  _send_tcp_request(action, payload)
    - Serializes request as JSON with nonce and timestamp
    - Encrypts with AES-GCM using stored key
    - Sends length-prefixed encrypted message
    - Receives and decrypts the response
    - Applies tcp_delay_ms from simulation config
    - Simulates error if random() < error_rate
    - Retries up to 3 times with reconnection on connection loss
    - Returns parsed JSON

  should_reevaluate(interval_requests=5, interval_seconds=10) -> bool
    - Returns True if 5 requests have been sent OR 10 seconds elapsed
    - This triggers re-probing in the adaptive client

  close_all()
    - Closes HTTP session and/or TCP socket cleanly

SESSION-WISE HANDSHAKE OPTIMIZATION:
  - Handshake time is measured ONLY during connect_tls() / connect_tcp()
  - Stored in self._last_handshake_time dictionary
  - After a switch or reconnect, the next logged request shows the handshake
  - All subsequent requests in the same session show handshake_time_ms = 0
  - This accurately represents real-world behavior where handshake is
    a one-time cost per session, not per request.

2.9  client/adaptive_client.py  (MAIN ORCHESTRATOR)
--------------------------------------------------------------------------------

PURPOSE: The MAIN SCRIPT that ties everything together. This is what
         you run to start the adaptive protocol selection experiment.

KEY FUNCTIONS:

  run_adaptive_client(num_requests, tls_host, tls_port, tcp_host, tcp_port,
                      switch_delay_at, low_delay, high_delay)
    
    This is the heart of the entire project. It:
    1. Initializes all components (prober, engine, hysteresis, session)
    2. Clears old logs and stop flag
    3. Probes both servers initially
    4. Evaluates which protocol to start with
    5. Connects using the chosen protocol
    6. Runs a loop of N requests:
       - Checks stop flag every iteration (allows clean termination)
       - At switch_delay_at, increases TLS server delay to simulate
         network degradation (via the /api/set_delay endpoint)
       - Every 5 requests, re-probes and re-evaluates
       - If hysteresis controller triggers: switches protocol
       - Logs every request to logs/session_log.json
       - On 3 consecutive errors: emergency switches to other protocol
    7. Prints summary report

  STOP FLAG MECHANISM:
    - get_stop_flag_path() -> logs/stop_flag.json
    - check_stop_flag() -> reads {"stop": true/false}
    - clear_stop_flag() -> resets to false
    - The dashboard Stop button writes {"stop": true}
    - The client checks this flag at the start of every request loop
    - This allows CLEAN termination without force-killing

  EMERGENCY PROTOCOL SWITCH:
    - Tracks consecutive_errors counter
    - After MAX_CONSECUTIVE_ERRORS (3) failures:
      * Force-switches to the other protocol via hysteresis.force_protocol()
      * Resets error counter
      * Attempts to reconnect
    - This ensures the system adapts even when reliability drops to zero

  SESSION-WISE HANDSHAKE LOGGING:
    - Tracks last_connected_protocol
    - Only logs handshake_time_ms when protocol changes or reconnects
    - Subsequent requests in same session log handshake_time_ms = 0

  get_log_path(), load_logs(), save_log_entry(), clear_logs()
    - File I/O functions for managing the JSON log file
    - Each log entry contains: request_id, timestamp, protocol, action,
      rtt_ms, handshake_time_ms, payload_size, tls_score, tcp_score,
      status, tls_components, tcp_components, request_type

3. HOW THE CUSTOM TCP SERVER WORKS (DEEP DIVE)
================================================================================

The custom TCP server is the KEY DIFFERENTIATOR in this project. Here's
exactly how it differs from a standard TLS server:

STANDARD TLS SERVER (our tls_server.py):
  [Client] ---> TCP 3-way handshake (SYN, SYN-ACK, ACK) ---> [Server]
  [Client] ---> TLS 1.3 Handshake:
                   ClientHello (cipher suites, extensions, ~200 bytes)
                   ServerHello (certificate ~2KB, key share, signature)
                   Client verifies certificate chain
                   Key derivation (HKDF with SHA256)
                   Finished messages
                   Total: 5+ messages, ~3-5 roundtrips
  [Client] <--> Encrypted HTTP request/response <--> [Server]

  Total initial overhead: TCP 3-way + TLS 1.3 handshake = 2-3 roundtrips
  Per-request overhead: HTTP headers (~200-400B) + TLS record layer + tags
  Handshake latency: 50-200ms (depending on CPU/network)

OUR CUSTOM TCP SERVER (tcp_server.py with ECDH + HKDF):
  [Client] ---> TCP 3-way handshake (SYN, SYN-ACK, ACK) ---> [Server]
  
  [Client] ---> HELLO + HMAC signature + timestamp --> [Server]
  [Server] ---> ECDH public key (PEM, ~100 bytes) --> [Client]
  [Client] ---> ECDH public key (PEM, ~100 bytes) --> [Server]
  
  Both perform ECDH key exchange and derive AES key via HKDF
  
  [Client] <--> Encrypted JSON (AES-GCM, length-prefixed) <--> [Server]

  Total initial overhead: TCP 3-way + ECDH exchange = ~1.5-2 roundtrips
  Per-request overhead: 4-byte length + 12-byte nonce + 16-byte tag + ciphertext
  Handshake latency: 5-20ms (no cert processing, just ECDH computation)
  
  NO HTTP headers, NO TLS record layer, NO certificate chain validation

WHY IS IT FASTER? (Despite ECDH being more complex than random key)
  1. No certificate (~2KB data) to transmit and verify
  2. No signature verification (CPU-intensive operations)
  3. No asymmetric key operations for client (ECDH is lightweight)
  4. No HTTP headers per request (~200-400B overhead)
  5. No TLS record layer framing (just 4-byte length prefix)
  6. Binary JSON vs HTTP's text protocol
  7. Total handshake: ~2-4 messages vs TLS's 5-7+ messages

WHY IS IT LESS SECURE THAN TLS?
  1. No server authentication (client doesn't verify server identity)
  2. No certificate chain (can't prove server is legitimate)
  3. HMAC uses pre-shared secret (not scalable to many clients)
  4. ECDH key exchange happens in plaintext over network
     (vulnerable to MITM without prior authentication)
  5. Relies on network-layer security (assumes trusted network)

TRADE-OFF JUSTIFICATION:
  - For LOCAL NETWORKS (lab, intranet, data center): This trade-off is
    acceptable because you control the network and can verify servers
    through other means (administrative access, trusted deployment)
  - For INTERNET: Use TLS. The extra security cost is necessary.
  - This project demonstrates the trade-off, not recommending insecure use
  - ECDH + HKDF provides MUCH better security than simple random key approach

4. HOW PROTOCOLS ARE ASSIGNED & SELECTION CRITERIA
================================================================================

PROTOCOL ASSIGNMENT HAPPENS IN 3 STAGES:

STAGE 1: INITIAL SELECTION (at startup)
  - The system starts with TLS by default (secure-first approach)
  - Immediately probes both servers to measure baseline performance
  - Decision engine computes 5-factor scores with normalized metrics
  - If TCP score is significantly better (>15%), may switch after 3 evals
  - More typically: Both protocols available, switching based on conditions

STAGE 2: PERIODIC RE-EVALUATION (every 5 requests or 10 seconds)
  - Adaptive client calls prober.probe_both()
  - Probes measure: handshake_time, RTT, payload_size for both protocols
  - Also considers configured error_rate from simulation_config.json
  - Decision engine normalizes all metrics to 0-1 range
  - Computes weighted scores: 0.30*latency + 0.20*handshake + 0.10*payload
                               + 0.25*security + 0.15*reliability
  - Hysteresis controller evaluates:
      IF recommended != current AND advantage > 15% AND 3 consecutive:
        SWITCH to new protocol
      ELSE:
        Stay with current protocol

STAGE 3: NETWORK CONDITION SIMULATION (dashboard-triggered)
  - Dashboard UI allows setting TLS delay, TCP delay, error rate
  - Settings written to logs/simulation_config.json
  - Client reloads config every 2 seconds
  - Server applies delays to new requests immediately
  - Next re-evaluation sees new metrics and may trigger switch
  - Example: TLS delay increases 200ms -> TCP becomes favored -> switch

SELECTION CRITERIA (The 5-Factor Scoring Formula):

  Score = 0.30 * norm_RTT + 0.20 * norm_handshake + 0.10 * norm_payload
          + 0.25 * security_cost + 0.15 * reliability_cost

  Where all factors normalized to 0-1 range:
    - norm_RTT = RTT / 3000ms (MAX_RTT = 3 seconds)
    - norm_handshake = handshake_time / 3000ms
    - norm_payload = payload_size / 2000B (MAX_PAYLOAD)
    - security_cost = 0.2 for TLS, 0.6 for TCP
    - reliability_cost = error_rate (direct 0-1 value)

  This design means:
    - 30% of score influenced by request latency
    - 20% by connection setup cost
    - 10% by data transfer size
    - 25% by security attributes (favors TLS)
    - 15% by reliability/packet loss

  WHY THESE WEIGHTS?
    - Latency (0.4): Most noticeable to users.
    - Handshake (0.3): Important for new connections, but paid only once.
    - Payload (0.1): Least impactful because both protocols send similar data.
    - Security (0.1): Gives TLS a consistent advantage in security-critical scenarios.
    - Reliability (0.1): When error rate increases, this penalizes the affected protocol.

6. METRICS EXPLAINED - WHAT EACH METRIC SPECIFIES
================================================================================

1. RTT (Round-Trip Time) [measured in milliseconds]
   WHAT: The time from sending a request to receiving the complete response.
   MEASURES: Network latency + server processing + encryption/decryption +
             injected artificial delay (from simulation config)
   WHY IT MATTERS: Directly affects user-perceived responsiveness.
   HOW MEASURED: time.perf_counter() before request, after response, difference.
   IN OUR PROJECT: TLS RTT includes HTTP + TLS record layer overhead + delay.
                   TCP RTT includes AES-GCM encryption + length-prefix + delay.

2. HANDSHAKE TIME [measured in milliseconds]
   WHAT: The time to establish a NEW connection from scratch.
   MEASURES: TCP connect + protocol-specific handshake overhead + delay.
   WHY IT MATTERS: Paid every time a new connection is created or after a switch.
   FOR TLS: Includes TCP 3-way handshake + TLS 1.3 handshake
            (ClientHello, ServerHello, certificate verify, key derivation).
   FOR TCP: Includes TCP 3-way handshake + HELLO->ACK exchange + AES key transfer.
   SESSION-WISE: Only logged for the FIRST request after a connect/switch.
                  Subsequent requests in the same session log 0ms.

3. PAYLOAD SIZE [measured in bytes]
   WHAT: The size of the response body.
   MEASURES: Data transfer volume per request.
   WHY IT MATTERS: Larger payloads mean more time spent in encryption/decryption
                   and more network bandwidth consumed.
   TLS vs TCP: TLS adds HTTP headers (~200-400 bytes overhead per response).
               Our TCP protocol has minimal framing (4-byte length + 28-byte crypto).

4. COST SCORE [dimensionless, computed]
   WHAT: Weighted combination of all five metrics.
   FORMULA: Score = 0.4*RTT + 0.3*handshake + 0.1*(payload/1000)
                    + 0.1*security_cost + 0.1*reliability_cost
   WHY IT MATTERS: Single number that captures overall protocol efficiency.
   LOWER = BETTER.

5. SCORE ADVANTAGE [measured in percentage]
   WHAT: How much better the winning protocol is compared to the losing one.
   FORMULA: (loser_score - winner_score) / loser_score * 100
   WHY IT MATTERS: Must exceed 15% threshold for hysteresis to consider switching.

6. CONSECUTIVE COUNT [count, 0-3]
   WHAT: Number of consecutive re-evaluations where the candidate protocol won.
   WHY IT MATTERS: Must reach 3 before switching is allowed.
   PREVENTS: Oscillation due to temporary network fluctuations.

7. SECURITY COST [dimensionless]
   WHAT: Penalty for using a less secure protocol.
   TLS: 1.0 (low cost = very secure)
   TCP: 5.0 (higher cost = less secure)
   WHY IT MATTERS: Ensures TLS has an inherent advantage in security-critical
                    scenarios, balancing pure performance metrics.

8. RELIABILITY COST [dimensionless]
   WHAT: Penalty based on error rate and historical volatility.
   FORMULA: error_rate * 1000 + volatility_penalty
   WHY IT MATTERS: When error rate increases (via dashboard), this cost rises,
                    making the affected protocol less attractive.
   DASHBOARD DISPLAY: Reliability Score = 1 - error_rate (shown on stats card)

9. ERROR RATE [0.0 to 1.0]
   WHAT: Configured probability of request failure.
   SET VIA: Dashboard "Error Rate (%)" control
   EFFECT: Prober may return failed probes. SessionManager may raise exceptions.
   DASHBOARD: Request Outcome chart shows failures in red.

7. BASIS OF COMPARISON BETWEEN TLS AND TCP
================================================================================

We compare the two protocols across these dimensions:

+--------------------+--------------------------+-----------------------------+
| DIMENSION          | TLS (Secure Mode)        | Custom TCP (Fast Mode)      |
+--------------------+--------------------------+-----------------------------+
| Transport          | HTTP/1.1 over TLS 1.3    | Raw TCP socket              |
| Port               | 5000                     | 6000                        |
| Encryption         | TLS 1.3 (cipher suite    | AES-256-GCM (hardcoded)     |
|                    | negotiated automatically)|                             |
| Handshake          | TLS 1.3 full handshake   | ECDH key exchange           |
|                    | (1-RTT, ~5-7 messages)   | (HMAC auth + ECDH, ~3 msgs) |
| Key Exchange       | ECDHE + certificate chain| ECDH only (no certs)        |
| Authentication     | X.509 certificate        | HMAC-SHA256 signature       |
| Forward Secrecy    | Yes (ECDHE per session)  | Yes (ECDH-derived key)      |
| Replay Protection  | Built-in (TLS nonces)    | Multi-layer (nonce+time+hash)|
| Framing            | HTTP headers + body      | 4-byte length prefix        |
| Overhead per req   | ~200-400 bytes headers   | 28 bytes (nonce + tag)      |
| Handshake latency  | HIGH (cert chain + sig)  | LOW (ECDH computation only) |
| Request latency    | MEDIUM (HTTP + TLS)      | LOW (minimal framing)       |
| Message Integrity  | TLS record layer         | AES-GCM tag + SHA256 hash   |
| Security level     | VERY HIGH                | MODERATE (no server auth)   |
| Standards          | IETF RFC 8446            | Custom (ECDH + HKDF + GCM)  |
| Key Derivation     | HKDF-SHA256 (1.3)        | HKDF-SHA256 (same as TLS)   |
+--------------------+--------------------------+-----------------------------+

KEY INSIGHT FROM OUR RESULTS:
  On same network with identical delays:
    TLS RTT: 85-120ms per request (includes HTTP + TLS overhead)
    TCP RTT: 30-40ms per request (minimal overhead)
  
  This ~2.5-3x difference demonstrates that:
  - TLS 1.3 handshake and HTTP headers carry measurable overhead
  - For latency-sensitive applications, lightweight protocols win
  - But TLS provides stronger security (cert verification, server auth)
  - TCP protocol trades server authentication for speed

8. NOVELTY & HOW THIS PROJECT ADDRESSES RESEARCH GAPS
================================================================================

The PDF identifies 4 specific research gaps. Here is how our project
addresses EACH one:


RESEARCH GAP 1: "Lack of Cross-Protocol Adaptive Selection Mechanisms"
  (Existing works optimize individual protocols but don't switch between them)
  
  HOW WE ADDRESS IT:
  Our system runs TWO fundamentally different protocols simultaneously
  and DYNAMICALLY SWITCHES between them at runtime. This is not about
  optimizing TLS or optimizing TCP -- it's about having BOTH available
  and choosing the right one for the current conditions.
  
  IMPLEMENTATION:
  - session_manager.py maintains connections to both servers
  - switch_to() method cleanly transitions between protocols
  - Both servers expose identical APIs so switching is transparent


RESEARCH GAP 2: "Focus on Handshake Optimization Rather Than Adaptive 
                 Decision Systems"
  (Studies reduce handshake latency but don't use metrics to DRIVE selection)
  
  HOW WE ADDRESS IT:
  Our decision_engine.py doesn't just MEASURE handshake cost -- it uses
  it as a FACTOR in a 5-metric scoring formula that actively DRIVES
  protocol selection. The handshake metric contributes 30% of the score.
  
  IMPLEMENTATION:
  - network_prober.py measures handshake time for both protocols
  - decision_engine.py uses it in the scoring formula
  - The score determines the recommended protocol


RESEARCH GAP 3: "Absence of Multi-Metric Decision Models for Protocol Selection"
  (Most research uses isolated parameters like latency OR security)
  
  HOW WE ADDRESS IT:
  Our decision engine uses FIVE distinct metrics combined with configurable
  weights into a SINGLE cost score:
  - RTT (latency) -> w1 = 0.4
  - Handshake time (setup cost) -> w2 = 0.3
  - Payload size (transfer efficiency) -> w3 = 0.1
  - Security cost -> w4 = 0.1
  - Reliability cost -> w5 = 0.1
  
  This is a TRUE multi-metric model. No single metric dominates; the
  weights can be tuned for different deployment scenarios:
  - Security-critical: increase security weight (prefer TLS)
  - Latency-sensitive: increase RTT weight (prefer faster protocol)
  - Unreliable network: increase reliability weight (prefer stable protocol)


RESEARCH GAP 4: "Limited Work on Stability-Aware Adaptive Switching"
  (No mechanisms like hysteresis for stable protocol adaptation)
  
  HOW WE ADDRESS IT:
  Our hysteresis_controller.py implements a FULL hysteresis mechanism:
  - 15% threshold: Candidate must show a SIGNIFICANT advantage
  - 3 consecutive checks: Must SUSTAIN that advantage, not just spike once
  - Safe switching: Only switches after request completion, not mid-stream
  
  This prevents the "oscillation problem" where a system switches back
  and forth rapidly due to minor network fluctuations, which would
  actually WORSEN performance (due to repeated handshake costs).
  
  IMPLEMENTATION:
  - consecutive_count tracks sustained advantage
  - threshold_pct prevents switching on marginal differences
  - switch_history records all transitions for analysis


ADDITIONAL NOVELTY:

  1. REAL-TIME VISUALIZATION:
     Unlike academic papers that show post-hoc analysis, our dashboard
     provides LIVE visualization of protocol switching behavior.
     You can watch the system adapt in real-time.

  2. CONFIGURABLE WEIGHTS:
     The decision engine weights can be changed via constructor arguments,
     allowing the system to be tuned for different priorities without
     code changes.

  3. DELAY & ERROR INJECTION:
     The dashboard allows DYNAMIC network condition changes
     (delay and error rate) during a running experiment, demonstrating
     live adaptation under controlled degradation.

  4. CLEAN SEPARATION OF CONCERNS:
     Each component (prober, engine, hysteresis, session) is independent
     and testable. This is a proper engineering architecture, not a
     monolithic script.

  5. SESSION-WISE HANDSHAKE OPTIMIZATION:
     Handshake cost is logged only once per session, not per request.
     This accurately represents real-world behavior and prevents
     misleading visualization of handshake overhead.

  6. EMERGENCY PROTOCOL SWITCH:
     If a protocol fails 3 consecutive times (e.g., due to high error rate),
     the system automatically switches to the other protocol.
     This ensures the system remains functional even under extreme
     network degradation.

  7. MANUAL API CLIENT:
     The manual_client.py demonstrates that this is a REAL API system,
     not just a simulation. Users can send individual requests via CLI
     and observe real-time adaptive behavior.
